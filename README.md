# 🚕 NYC Uber Fare Predictor

Predicts NYC Uber/taxi fares from pickup/dropoff location, trip time, and
passenger count —> trained on the [Kaggle NYC Taxi Fare Prediction
dataset](https://www.kaggle.com/c/new-york-city-taxi-fare-prediction) and
served through an interactive Streamlit app.

## Results

| Model | R² | MAE | RMSE |
|---|---|---|---|
| Linear Regression (Ridge) | 0.8247 | $1.965 | $3.964 |
| XGBoost | 0.8521 | $1.838 | $3.640 |
| **LightGBM (deployed)** | **0.8545** | **$1.825** | **$3.611** |
| Ensemble (XGBoost + LightGBM) | 0.8541 | $1.827 | $3.616 |

LightGBM is the best-performing model and the one served by the app —
predicting fares within **$1.83 on average** on held-out test data.

## Debugging story

The first version of this pipeline trained a plain `LinearRegression` on
`log1p(fare_amount)` and inverted predictions with `np.expm1()`. That gave
an **R² of -157,006**  not a weak model, a broken one.

Root cause: a few of the raw features were near-collinear (`hour` vs. its
own derived `is_rush_hour`/`is_night` flags, `weekday` vs. `is_weekend`),
which destabilized ordinary least squares' coefficients. With no bound on
the model's output, a single unstable log-space prediction on one test row
turned into an astronomical dollar value after `expm1()` (`expm1(20) ≈
$485 million`), which alone was enough to wreck the R² across the entire
test set.

Fix, in two parts:
1. **Removed the collinearity at the source**  replaced raw `hour`/
   `weekday`/`month` integers with cyclical sin/cos encodings, and swapped
   plain `LinearRegression` for L2-regularized `Ridge` inside a
   `StandardScaler` pipeline.
2. **Added a safety net** — every model's log-space prediction is clipped
   to a sane range (derived from the training target's own range) before
   being inverted back to dollars, so no single row can ever produce an
   absurd prediction regardless of which model is deployed.

Full details are in the notebook (`notebook/eda_and_model_comparison.ipynb`,
section 6).

## Features

**Modeling pipeline**
- Haversine distance between pickup/dropoff coordinates
- Airport-proximity flag (JFK/LGA/EWR) for flat-fare trips
- Cyclical (sin/cos) encodings for hour, weekday, and month
- Trained on `log1p(fare)`, evaluated in dollars via a clipped inverse
  transform
- Four candidates compared (Ridge, XGBoost, LightGBM, weighted ensemble);
  best model on test R² is auto-selected and saved

**App** (`app.py`)
- Interactive map (pydeck) with pickup/dropoff pins and a route colored by
  an estimated traffic-conditions proxy (time-of-day based, clearly
  labeled as an estimate, not live traffic data)
- Per-prediction SHAP explanation — a waterfall chart showing exactly how
  much each feature pushed that specific fare up or down, in dollars
- Shareable trip links via URL query parameters
- Out-of-training-region warning for coordinates outside NYC
- Session history table of predictions made so far
- Model performance tab pulling live from `models/metrics.json`

## Setup (local)

```bash
git clone https://github.com/YOUR_USERNAME/uber-fare-prediction.git
cd uber-fare-prediction
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Download the dataset from
[Kaggle](https://www.kaggle.com/c/new-york-city-taxi-fare-prediction) and
place it at `data/uber.csv`.

Train the models:

```bash
python src/train.py
```

This writes `models/best_model.joblib` and `models/metrics.json`.

Run the app:

```bash
streamlit run app.py
```

## Deploying (Streamlit Community Cloud — free)

1. **Push the repo to GitHub**, including `app.py`, `src/`, `requirements.txt`,
   and `models/` (the trained `.joblib` + `metrics.json` — train locally
   first and commit these so the deployed app doesn't need to retrain).
   - `data/uber.csv` is ~190k rows; if it's too large for a normal GitHub
     push, either use [Git LFS](https://git-lfs.com/) or skip committing it
     entirely — the app only needs `data/uber.csv` for the optional SHAP
     background sample, and degrades gracefully (shows a warning instead
     of crashing) if it's missing.
2. Go to [share.streamlit.io](https://share.streamlit.io) and sign in with
   GitHub.
3. Click **"New app"**, select your repository, branch (`main`), and set
   the main file path to `app.py`.
4. Click **Deploy**. Streamlit Community Cloud installs everything from
   `requirements.txt` and starts the app — first deploy usually takes a
   couple of minutes.
5. Once live, copy the app's URL into the **Live demo** line at the top of
   this README.
6. Any future `git push` to the connected branch auto-redeploys the app.

If the deploy fails on missing packages, double check `requirements.txt` is
at the repo root (not inside `src/`) — that's the only file Streamlit Cloud
reads for dependencies.
